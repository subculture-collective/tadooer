# Assistant capability and permission inventory

Issue #19; follow-on operations #32. Baseline: branch from issue #18 at `4664bb1`.
This inventory describes source support, not successful real Codex/Claude operation.
The installed stdio smoke tests and exact-client qualification (#39) are separate.

## Authority and confirmation

`packages/contracts/src/index.ts` exports the sole automation catalog. Each row
below references those IDs; the catalog supplies exact scopes, schemas, HTTP/MCP
names and whether preview is required. Do not maintain a second hand-written
permission list. Read resources also appear as MCP tools. The confirmation tool
resolves the scope of the stored operation rather than requiring every advertised
write scope. Browser identity, provider secret entry, OAuth consent and issuance
of broader assistant authority remain owner-interactive boundaries.

All current mutation tools use preview/confirmation. A server confirmation call
is not necessarily a second user prompt: #33 will qualify ordinary explicitly
requested edits versus explicit bulk/deletion approval. Existing scope, revision,
staleness and durable replay checks must remain. Skills do not replace these
application controls. No full-capability claim is made while gaps remain.

## Drift checks and coverage boundary

`assistant-capabilities.json` contains the concrete web API function names,
source references and authority notes. `automation-coverage.test.ts` uses the
TypeScript syntax tree to require a disposition for every exported browser API
function, and requires a mapping for every automation catalog entry. It rejects
unknown IDs, duplicate API mappings, missing source paths and untracked gaps.
Adding a callable browser export or a catalog operation requires updating the
inventory. This prevents catalog/API drift; it does not prove behavioral parity.

Local-only navigation, filters, command-bar presentation and recovery diagnostics
are client presentation, not separate persisted assistant actions. Query/read
capabilities should support their user outcome without simulating UI controls.
Any newly added server-backed UI action must use the reviewed API boundary or
add an explicit inventory row. Habits are recorded separately because the UI
uses sync commands instead of exported direct-HTTP habit functions. The calendar
ICS download is also mapped explicitly because it uses an authenticated anchor
in `calendar-migration.tsx`, outside the API helper module.

## Evidence required for each implementation slice

1. Shared input/output/scope contracts, owner isolation and authoritative store.
2. Rejected/stale preview, revoked credentials, race, interrupted confirmation,
   atomic rollback, restart/replay and deletion-after-restore tests as applicable.
3. Installed runtime initialize/catalog/read/preview/confirm checks.
4. Actual Codex and Claude workflow evidence under #39, including skill behavior,
   approval rejection and no secret disclosure. Claude account access is deferred.
5. Update this inventory and linked implementation issue; deployment remains #37.

Project/tag lifecycle now uses dedicated write scopes. Task assignment retains `tasks:write` and validates owner, active destination, task revision and frozen destination revisions. New scopes must be explicitly provisioned; existing tokens are not broadened. These four operations use the existing preview/confirm protocol, with entity, sync, consumed preview, receipt and audit committed together. Live client qualification remains #39.

Organization parity (#28, ADR 0019) extends `projects.mutate` with `complete`, `reopen` and `configure` (colour, icon, hide-from-menu, backlog), and `tags.mutate` with `configure` (colour, icon). `projects.reorder` and `tags.reorder` freeze every record's revision, so any edit before confirmation makes the preview stale. `projects.set_backlog` binds the project revision and checks the task's project again at confirmation. Notes use new `notes:read` and `notes:write` scopes; `notes.mutate` covers create, update, complete-membership reorder and permanent delete. Notes are online-only records outside the sync feed.

Linked issues and attachments (#30, ADR 0021) use new `task_links:read` and `task_links:write` scopes. `task_links.get` returns one task's imported issue link and attachments. `task_links.mutate` adds, edits or removes link and note attachments, and removes an issue link, with frozen revisions. Previews name the link host, not the full address. No operation polls, refreshes or writes to an issue provider: that needs a fresh provider authorization, which does not exist yet.

Imported plugin data (#66, ADR 0026) uses a new `plugin_data:read` scope. `plugin_data.list` returns each imported plugin's enabled flag and each data entry's plugin ID, key, size and format. No assistant operation returns the data itself or deletes a record: download and permanent deletion stay with the owner in the browser. Tadooer has no plugin runtime, so there are no plugin actions to expose.

Checklist reads use `tasks:read`; mutations use `tasks:write`. Previews bind the parent task revision and item revisions. Reorder validates complete membership again at confirmation, including newly added items; deleted items emit sync tombstones. Atomic receipts prevent confirmed deletions from being executed twice. This is the existing checklist model, not full hierarchy (#27).

Planning and notification preference reads include a persisted revision (zero for unstored defaults). Dedicated write scopes use that revision in preview/confirmation. Browser writes advance the same revision; change-away-and-back is stale. Enabling notifications may permit later scheduled worker delivery, which the preview states; confirmation does not send a test notification.

Test notifications require `notifications:test` and a revision-bound preview. Confirmation returns a durable pending delivery ID, committed with the audit and replay receipt. The worker sends fixed test content to the configured owner destination, even with scheduled reminders disabled. Replaying confirmation never queues another send; uncertain sends fail without retry. Read `notifications.delivery` with the receipt delivery ID for its current state, or `notifications.status` for aggregate delivery health. Delivery reads are owner-scoped and redact task content and publisher configuration. Actual installed client qualification remains #39.

Archived history (#38, ADR 0022) uses the existing task scopes. `tasks.history` is a `tasks:read` resource with an optional `query` (title and notes, ASCII case-insensitive), `cursor` and `limit` (1–200). Each entry is a top-level archived task with the children archived with it and read-only import provenance: source store, review reasons and unresolved historical references. `tasks.archive` and `tasks.unarchive` use `tasks:write`; the preview names the task, counts its children and freezes every revision in the family. A child cannot be archived or restored alone, and a running focus session or calendar block in the family blocks archiving. Archived tasks cannot be edited; a restore returns them to active tasks without changing completion or dates.

Work history (#41, ADR 0024) uses the existing task scopes. `time.report` is a `tasks:read` resource for an inclusive range of owner-zone days (`from`, `to`, at most 366 days). It returns day, week, task and project totals, estimates, imported work start/end records and every entry with its source: focus (read-only, projected from session intervals), import or manual. `time_entries.mutate` uses `tasks:write` to add, edit or delete an import or manual entry. An addition supplies its entry ID and may be negative to correct focus time. The preview names the task, the day and the resulting day total, and freezes the entry revision (or the task revision for an addition). Confirmation checks again that the task-day total stays between 0 and 24 hours and that a running focus session is not lowered. Archived history and focus entries cannot be changed.

Counters and daily evaluations (#64, ADR 0025) use new `metrics:read` and `metrics:write` scopes. `counters.history` returns counter definitions with their derived streak, the owner's today and zone, and day values for an inclusive range of at most 366 owner-zone days; `evaluations.list` returns evaluations and Tadooer focus time per day for the same kind of range. `counters.mutate` creates, edits or deletes a definition; edits and deletes freeze the counter revision, and a delete removes the counter's recorded days. `counters.record` sets or increments one day with the day revision the assistant read (0 for an empty day), or starts or stops a stopwatch with the counter revision; the preview states the value before and after, and confirmation checks the day revision and the value bound (1,000,000 counts, or the day's 23 to 25 hours for a stopwatch) again. `evaluations.write` creates or edits one day's evaluation with its revision. Imported Super Productivity focus sessions are read-only evaluation history and never become time entries.

Saved day order (#98, ADR 0027) uses the existing task scopes. `day_order.get` is a `tasks:read` resource for one calendar `date`; without a date it reads the owner's current planning date, which honours the planning day start. It returns the order's revision (0 before the first save) and every current member: the open, active, date-only tasks planned for that date, saved ranks first. `day_order.reorder` uses `tasks:write` and needs the current revision and every member exactly once. A day order has no entity ID to freeze, so the preview names the date and tasks, and confirmation repeats the revision and membership checks inside its transaction; a browser reorder or a task joining or leaving the day in between makes the preview stale. The browser's plan-tomorrow action has no dedicated tool: the assistant sets planned days with `tasks.update` and then reorders, so this row is partial.
